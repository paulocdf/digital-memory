# Accessibility Audit — 2026-04-25

Audit conducted as part of Phase B of the post-Phase-10 polish roadmap. Focus: WCAG 2.1 AA contrast for project theme accents and quick VoiceOver/screen-reader sanity checks.

## Methodology

- WCAG contrast ratios computed via the standard relative-luminance formula (`L = 0.2126·R + 0.7152·G + 0.0722·B` with sRGB linearization).
- Backgrounds tested: `#ffffff` (light mode body) and `#1e1e1e` (dark mode body).
- Foregrounds: white (`#fff`) which the codebase uses extensively as text-on-accent (95+ `color: #fff` rules).
- WCAG thresholds: **4.5:1** normal text, **3.0:1** large text and UI components.

## Findings

### F1 — Critical: white text on light accents fails AA (4 themes)

**`sunset`, `citrus`, `ocean`, `neon`** all fail the white-on-accent contrast threshold. These accents appear as backgrounds in `project-detail-banner`, the kanban "single project" header strip, and various pill/badge elements that inherit `color: #fff` from CSS rules.

**`citrus` (1.97:1) and `sunset` (2.70:1)** are the most severe — they fail even the relaxed 3:1 large-text/UI threshold. Any text rendered white on these accents is essentially unreadable for users with low vision.

**Recommended fix (deferred — out of scope for Phase B docs-only)**:
Add a `dmReadableFg(hex)` helper that picks `#fff` or `#1f1f1f` based on accent luminance (threshold ~0.55). Apply it via a CSS variable `--pj-accent-fg` set in `dmApplyProjectTheme`. Then replace `color: #fff` in project banners with `color: var(--pj-accent-fg, #fff)`. Roughly a 1-day change touching 5–8 selectors in `project-list.html`, `kanban-board.html`.

### F2 — Dark-mode accent text fails AA (4 themes)

**`mono`, `terminal`, `lavender`, `paper`** all fail the 4.5:1 threshold when the accent is rendered as text/icon color on the dark body background. These accents primarily affect:
- Filter pill labels in dark mode
- Sidebar project glyph dot accents
- `--pj-accent` borders/dividers (3:1 UI threshold, where `mono` 1.66 still fails)

**Recommended fix (deferred)**: introduce per-theme `accentDark` field; `dmApplyProjectTheme` switches based on `document.documentElement.dataset.theme`. The default fallback `color-mix(var(--pj-accent), white 30%)` would fix most cases automatically.

### F3 — `accent2` on light fails AA across the board

`accent2` is currently used for **gradient endpoints** (banner gradients) and decorative trims, not for text or UI components. **No fix needed** — the contrast failures are not consequential because `accent2` is not used as a foreground for legible content.

If `accent2` is later promoted to a text/icon role, several themes would need stronger second colors.

### F4 — VoiceOver sanity (manual spot-check, no concrete failures)

Phase 10 already addressed the high-impact ARIA gaps (radiogroups, segmented controls, label remove buttons, sidebar project glyphs marked decorative). No new VoiceOver-blocking issues identified in this pass for:

- Kanban column accent picker (radiogroup + roving tabindex, post-Phase A)
- Legacy color picker (radiogroup + arrow-key nav, post-Phase A)
- Project detail banner (heading + description in semantic order)
- Inline task edit panel (form labels present, segmented controls have group roles)

A deeper screen-reader pass with a real VO/NVDA user is recommended before claiming AA conformance.
